关注一个公众号很轻，整理两百多个公众号很重。

我的微信里，公众号列表已经积到了 236 个。里面有还在看的，有早就停更的，也有当年因为一篇文章顺手关注、后来再没打开过的。

微信可以逐个取消关注，但当这个动作要重复上百次时，问题就不只是“麻烦”。人会看错，会漏掉，也会在连续点击以后忘记哪些必须保留。

所以我做了一个 Mac 应用，名字很直接：**公众号整理**。

它不是“一键清空”。我更想做的是一条不容易误操作的整理流程：

- 先读取公众号列表，按名称或账号 ID 搜索；
- 把重要账号加入白名单；
- 跨页勾选想处理的账号；
- 先生成一份具体清单；
- 再次确认后逐个取关；
- 每处理一个，都马上查询是否真的取消成功；
- 最近 30 天的记录里，还可以重新关注。

## 批量工具最重要的不是快，而是会停

我一开始也很容易把注意力放在“能不能全选”上。真正接入以后才发现，全选只是最简单的一步。

危险的是：账号切换了，程序还拿着旧清单；网络回执不明确，程序却当成成功继续跑；用户点击两次，队列重复执行；重要账号进了白名单，但某一层代码忘了检查。

现在白名单会在三个地方生效：界面上不能勾选，生成清单时再次排除，真正执行前还会再检查一次。

清单也会绑定当前微信账号和当前微信进程。只要切换账号或重启微信，旧清单就不能直接执行。遇到超时、状态不一致或结果无法确认，队列会暂停，而不是带着不确定性继续处理下一个。

我给这些路径写了 17 项隔离测试。它们不会操作真实微信，但会反复检查账号隔离、重复执行、停止继续、异常暂停、恢复关注和记录过期这些容易出事的地方。

## 为什么已经看到了列表，还让我打开小程序

如果你试过早期版本，可能会看到一个很奇怪的画面：右边明明已经有完整列表，下面却用红字提示“请打开一个微信小程序”。

这里其实混了两个状态。

列表来自上次成功读取后保存在本机的缓存。即使连接断开，它仍然可以用来搜索、筛选、维护白名单和生成清单。

但真正执行取关时，应用需要恢复与当前微信会话的实时连接。这个连接借助一个已经打开的小程序页面建立，所以执行前仍然需要打开任意一个小程序，并保持它的窗口存在。

逻辑没有冲突，原来的文案却把人搞糊涂了。现在界面会明确区分：

- **本机缓存列表**：可以继续整理，不能立即执行；
- **实时连接已建立**：核对清单后可以开始取关。

清单不会因为断线消失，恢复连接以后还能继续。

## 当前为什么只支持 Apple Silicon

这个应用不只有 Swift 写的 Mac 界面，还打包了 Node.js、Python 和 Frida 的原生组件。

我目前只有 Apple Silicon Mac，也只完成了 arm64 的真实验证。没有 Intel 机器，就很难认真验证从启动、连接到取关复核的完整流程。

因此我没有做一个“理论上兼容”的 Universal 包，而是先明确标注：**仅支持 Apple Silicon，不支持 Intel Mac。**

以后真要支持 Intel，需要在真实 Intel 环境或 Intel CI runner 上重新构建每个原生依赖、跑完整测试、合并架构，再重新签名和公证。它不是勾选一个选项就结束的事。

## 我决定先开源，不收费

底层调试通道依赖 [WMPFDebugger](https://github.com/evi0s/WMPFDebugger)。它采用 GPLv2 许可证。

GPL 不是“不能收费”。它允许收费分发，但如果分发了受 GPL 约束的程序，也要向接收者提供相应源码，并保留对方继续修改和分发的自由。

另外，上游 README 还明确说明，其中一部分代码来自微信开发者工具、版权归腾讯。GPL 的商业许可不等于同时获得了腾讯或微信的商业授权。

综合考虑，我选择先把应用完整开源，不收费。仓库里不只放了自己的代码，还保留了固定版本的上游源码、本地修改记录，以及 Node.js、Frida、Python 等所有随包组件的许可证。

当前也没有提供一个“下载即用”的正式安装包。它还是一款实验性开发者工具：只支持经过验证的微信版本，使用前需要自己构建，尚未完成 Apple Developer ID 签名和公证。

如果你也有一个越来越长的公众号列表，或者对这套安全设计、macOS 打包、GPL 合规过程感兴趣，可以在 GitHub 看源码：
