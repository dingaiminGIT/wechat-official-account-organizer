微信公众号有一种很安静的膨胀方式。

关注一个号只需要几秒，几年下来，列表却会长到几百个。真正想整理时，麻烦才出现：我要先判断哪些还值得留，再逐个进入资料页取消关注。这个动作本身不难，难的是重复两百多次以后，人很容易选错、漏掉，或者忘记自己刚才处理到了哪里。

我自己的微信里读到了 236 条公众号记录。于是我做了「公众号整理」，一款运行在 Mac 本机的工具：先把列表变得可搜索、可分类，再用白名单和二次确认清单保护重要账号，最后逐个执行并复核结果。

项目源码已经公开：

[GitHub：wechat-official-account-organizer](https://github.com/dingaiminGIT/wechat-official-account-organizer)

当前版本只支持 Apple Silicon，不支持 Intel Mac，也还没有做 Developer ID 签名和 Apple 公证，所以现阶段提供的是源码与构建说明，而不是面向所有人的免配置安装包。

## 它不只是一个“全选”按钮

工具现在提供这些能力：

- 按公众号名称或账号 ID 搜索；
- 在多个分页之间保留选择；
- 把重要账号加入白名单，批量选择时自动排除；
- 先生成一份明确的取关清单，确认后才真正执行；
- 串行处理，每完成一个账号都立即查询关注状态；
- 结果不确定时暂停，不自动重试可能已经成功的操作；
- 保存最近 30 天的取关记录，并支持重新关注；
- 微信连接断开后保留缓存列表，恢复连接后再执行原清单。

这里最重要的产品决定，是把“选择”和“执行”拆开。

选择可以很快，全选也可以跨页。但只要还没有生成清单，什么都不会发生。清单会列出具体账号，用户再次点击“开始取关”才进入队列。白名单则同时存在于前端禁选、服务端生成清单、执行前校验三个位置，避免某一层状态出错后直接伤到重要账号。

## 为什么已经看到列表，还要打开小程序

这是开发中最容易让人困惑的一处。

页面里其实有两个不同状态：一个是上次读取后保存在本机的账号列表，另一个是 WMPFDebugger 与微信小程序之间的实时调试连接。前者还在，所以列表可以继续搜索、勾选、维护白名单；后者断开时，应用不能安全地向当前微信会话发送取关或恢复关注操作。

旧界面只说“请打开小程序”，看起来就像已经拿到列表还在重复要求同一件事。现在我把它改成了两个明确提示：黄色的“本机缓存列表”和绿色的“实时连接已建立”。缓存模式下仍可生成清单，只有准备执行时才需要重新打开一个小程序恢复连接，清单不会因此丢失。

小程序在这里不是数据来源页面，而是调试通道的载体。只停在微信的小程序列表不够，需要真正打开任意一个小程序的内容页，并在执行期间保持窗口打开。

## 我更在意“停下来”的能力

批量操作的危险，往往不是第一项失败，而是第一项失败以后程序还继续跑。

因此执行队列遵循几个硬规则：

1. 清单绑定当前微信账号和当前进程会话。切换账号、重启微信或打开旧页面，都不能直接继续执行旧清单。
2. 每次只处理一个账号。成功回调之后，还要重新查询 `IsSubscribed`，确认状态确实变成未关注。
3. 请求超时、回执异常或状态不一致时，队列暂停。它不会假装成功，也不会自动重试一次具有副作用的操作。
4. 用户点击继续时，工具先重新查询状态。已经取消关注的账号会跳过，避免重复发送。
5. 退出应用时停止后续队列，等待当前账号完成复核，再关闭它自己启动的调试服务。

现在仓库里有 17 项 Python 隔离测试，覆盖账号切换、白名单隔离、重复执行、未知结果暂停、停止与继续、恢复关注、记录过期和环境不兼容等路径。测试不能消除平台风险，但至少能把“程序自身不该犯的错”变成可重复检查的约束。

## 技术上是怎样串起来的

Mac 外壳使用 Swift 和 AppKit，内容界面由内置的本机网页服务提供。Python 负责状态管理、账号隔离、清单和串行队列，TypeScript 操作器通过 CDP 调用微信公众号页面已有的结构化能力。

真正建立调试通道的是 [WMPFDebugger](https://github.com/evi0s/WMPFDebugger)，它借助 Frida 与微信的小程序进程连接。我的项目固定使用它的一个具体提交，没有在用户机器上自动拉取最新版，并对本地版本增加了回环地址绑定、CDP 令牌、连接健康查询和安全退出。

我没有读取微信聊天数据库，也没有导出登录凭据。账号列表、白名单和执行记录保存在 `~/Library/Application Support/com.baiya.WeChatOrganizer`，按本机账号隔离；仓库和应用包不包含我的真实列表。

兼容性同样采取白名单思路。当前只允许我真实验证过的 macOS、微信与 WMPF build 组合，并核对相关组件的 SHA-256。遇到未知版本就暂停接入，不自动降级微信，也不关闭系统保护。

## 为什么先标注“仅支持 Apple Silicon”

Swift 界面本身可以做通用二进制，但这个应用还打包了 Node.js、Python 运行时和 Frida 原生绑定。只要其中任何一项只有 arm64，整个应用就不能算 Intel 兼容。

我手上没有 Intel Mac，也没有完成真实 Intel 环境验证。与其生成一个看起来是 Universal、实际走不到完整流程的安装包，不如先把边界写清楚。当前构建脚本会直接检查 arm64，应用的关于窗口和项目介绍也都明确标注只支持 Apple Silicon。

以后如果要支持 Intel，常规做法是在 Intel runner 或真实 Intel Mac 上分别构建并跑完整验证，再用 `lipo` 合并原生组件，最后重新签名、公证。那是一个独立的兼容性项目，而不是改一个编译参数。

## WMPFDebugger 的 GPLv2，究竟意味着什么

WMPFDebugger 的 `package.json` 和 README 标明许可证为 `GPL-2.0-only`。GPL 并不禁止收费，但它要求在分发受许可约束的二进制或修改版本时，继续向接收者提供相应源码、保留版权和许可证声明，并允许对方在同一许可证下继续使用、修改和分发。

因此我选择把当前应用整体按 GPL-2.0-only 开源，而不是把依赖藏在安装包里。仓库里包含：

- 根目录的 GPLv2 许可证；
- 固定版本的 WMPFDebugger 源码；
- 单独的本地修改说明；
- Node.js、Frida、Python、PyInstaller、protobufjs、ws 等组件的许可文本；
- 构建应用内与二进制对应的 `Resources/Source` 和 `Resources/Licenses`。

还有一个必须单独说明的边界：WMPFDebugger 上游 README 表示，其 `src/third-party` 文件来自微信开发者工具，版权归腾讯控股有限公司。GPL 允许商业分发，不代表腾讯或微信同时授予了商标、平台接口或相关代码的商业授权。

所以我的决定是：现阶段先开源、先把用途和风险讲清楚，不收费，也不把它包装成一个可以长期稳定售卖的消费软件。如果以后真的要商业化，我会先重新评估依赖替代方案、平台条款、签名公证、兼容测试和法律风险，而不是只在下载页加一个付款按钮。

## 现在适合谁

它目前更适合愿意读构建说明、理解实验性工具边界，并且有 Apple Silicon Mac 的开发者。第一次使用时请先选一两个不重要的账号验证，不要上来就全选两百个。

我会继续把它当作一个“谨慎的软件”来维护：版本不确定就停，结果不确定就停，账号不一致就停。批量工具的价值不只在于替人省下多少次点击，也在于它知道什么时候不能继续。
